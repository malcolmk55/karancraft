# نقش‌ها و مدیریت سیستم — طرح دسترسی و عملیات مدیریتی

> این سند سیستم مدیریت نقش‌ها (RBAC)، جریان‌های کاری مدیریتی، و سطوح دسترسی هر نقش را تشریح می‌کند. ساختار داده‌ی مرتبط در `05-backend-and-data-architecture.md` تعریف شده است.

## ۱. تعریف نقش‌ها

سیستم سه نقش اصلی دارد:

### ادمین (Admin)
**توضیح:** مدیر کل سیستم با دسترسی به تمام عملیات مدیریتی و داده‌ها.

**دسترسی‌ها:**
- ایجاد، ویرایش و غیرفعال‌سازی کاربران (پزشک، منشی، ادمین دیگر)
- تعریف و مدیریت مطب‌ها
- اختصاص پزشک و منشی به مطب‌ها
- مشاهده‌ی تمام داده‌های بیماران، ویزیت‌ها، و ارتباطات (فقط‌خواندنی، برای پشتیبانی و نظارت)
- مشاهده‌ی لاگ ممیزی
- مدیریت طرح‌های اشتراک و وضعیت پرداخت پزشکان
- تنظیمات عمومی سیستم
- مدیریت قالب‌های تخصصی

### پزشک (Doctor)
**توضیح:** کاربر اصلی سیستم که ویزیت ثبت می‌کند و به پرونده‌ی بیمارانش دسترسی دارد.

**دسترسی‌ها:**
- مشاهده و ویرایش پروفایل خود
- دسترسی به بیماران خود از تمام مطب‌هایش
- ایجاد، مشاهده و ویرایش ویزیت‌ها
- جست‌وجوی پزشکان دیگر و ارسال/پذیرش درخواست ارتباط
- اشتراک‌گذاری بیمار با پزشکان متصل
- مشاهده‌ی بیمارانی که سایر پزشکان با او به اشتراک گذاشته‌اند
- مدیریت اشتراک و پرداخت خود
- مشاهده‌ی آمار و تحلیل‌های مطب خود

### منشی مطب (Receptionist)
**توضیح:** کاربر عملیاتی که اطلاعات پایه‌ی بیماران را ثبت می‌کند تا پزشک نیازی به پر کردن فرم‌های اولیه نداشته باشد.

**دسترسی‌ها:**
- ایجاد پرونده‌ی بیمار جدید (اطلاعات پایه: نام، تلفن، کدملی، تاریخ تولد، جنسیت)
- ویرایش اطلاعات پایه‌ی بیماران مطب خود
- جست‌وجوی بیماران مطب خود
- مشاهده‌ی لیست بیماران (بدون جزئیات پزشکی ویزیت‌ها)

**محدودیت‌ها:**
- ❌ دسترسی به جزئیات ویزیت‌ها (شرح حال، تشخیص، نسخه)
- ❌ ایجاد یا ویرایش ویزیت
- ❌ مشاهده‌ی ارتباطات پزشکان
- ❌ دسترسی به بیماران مطب‌های دیگر
- ❌ اشتراک‌گذاری بیمار

## ۳. جریان ایجاد کاربر (توسط ادمین)

```
ادمین وارد پنل مدیریت می‌شود
    │
    ├── «افزودن کاربر جدید» را انتخاب می‌کند
    │
    ├── فرم ایجاد کاربر:
    │   ├── نام کامل
    │   ├── ایمیل (برای ورود)
    │   ├── رمز عبور اولیه
    │   ├── نقش: [ادمین | پزشک | منشی]
    │   │
    │   ├── اگر نقش = پزشک:
    │   │   ├── شماره‌ی نظام پزشکی
    │   │   ├── تخصص(ها)
    │   │   └── اختصاص به مطب(ها)
    │   │
    │   └── اگر نقش = منشی:
    │       └── اختصاص به مطب
    │
    ├── تایید و ایجاد
    │
    └── سیستم:
        ├── ایجاد رکورد User + Doctor/Receptionist
        ├── ارسال ایمیل خوش‌آمد با رمز اولیه
        ├── الزام تغییر رمز در اولین ورود
        └── ثبت در لاگ ممیزی
```

## ۴. احراز هویت (Authentication)

### ۴.۱. مکانیزم ورود

- **روش اصلی:** ایمیل + رمز عبور
- **توکن:** JWT با زمان انقضای کوتاه (۱۵ دقیقه) + Refresh Token (۷ روز)
- **ذخیره‌ی توکن:** HttpOnly cookie (نه localStorage) برای جلوگیری از حمله‌ی XSS

### ۴.۲. سیاست‌های رمز عبور

- حداقل ۸ کاراکتر
- ترکیبی از حروف بزرگ، کوچک، عدد و نماد
- هش‌شده با bcrypt (حداقل ۱۲ دور)
- الزام تغییر رمز اولیه در اولین ورود
- قفل شدن حساب پس از ۵ تلاش ناموفق (به‌مدت ۱۵ دقیقه)

### ۴.۳. نقشه‌راه آینده

- **احراز هویت دو مرحله‌ای (2FA):** پیامک یا اپلیکیشن احراز هویت — اولویت بالا برای حساب‌های پزشک
- **ورود با شماره‌ی موبایل + کد یکبار مصرف:** گزینه‌ی جایگزین برای پزشکانی که ایمیل استفاده نمی‌کنند
- **SSO سازمانی:** برای بیمارستان‌ها و مراکز بزرگ (فاز بعدی)

## ۵. پنل مدیریت ادمین

### ۵.۱. داشبورد ادمین

صفحه‌ی اصلی ادمین شامل:
- تعداد کل کاربران فعال (تفکیک نقش)
- تعداد مطب‌ها
- تعداد بیماران ثبت‌شده
- تعداد ویزیت‌های امروز/هفته/ماه
- وضعیت اشتراک‌ها (فعال، منقضی، نزدیک به انقضا)
- هشدارهای امنیتی (تلاش‌های ورود ناموفق، تغییرات مشکوک)

### ۵.۲. مدیریت کاربران

- لیست کاربران با فیلتر (نقش، وضعیت فعال/غیرفعال، مطب)
- ایجاد کاربر جدید (جریان بخش ۳)
- ویرایش اطلاعات کاربر
- غیرفعال‌سازی کاربر (soft delete — داده‌ها حفظ می‌شود)
- بازنشانی رمز عبور

### ۵.۳. مدیریت مطب‌ها

- ایجاد مطب جدید
- ویرایش اطلاعات مطب
- اختصاص/حذف پزشک و منشی از مطب
- مشاهده‌ی آمار هر مطب

### ۵.۴. لاگ ممیزی

- جست‌وجو و فیلتر بر اساس: کاربر، نوع عملیات، بازه‌ی زمانی، موجودیت
- خروجی CSV/Excel برای گزارش‌دهی
- نمایش جزئیات هر رکورد (قبل/بعد تغییرات)

## ۶. جریان کاری منشی مطب

### ۶.۱. هدف اصلی

منشی اطلاعات اولیه‌ی بیمار را پیش از ورود به اتاق پزشک ثبت می‌کند تا:
- پزشک وقت خود را صرف تایپ اطلاعات پایه نکند
- فرایند ویزیت سریع‌تر شود
- اطلاعات تماس و هویتی بیمار دقیق ثبت شود

### ۶.۲. جریان ثبت بیمار جدید (توسط منشی)

```
منشی وارد سیستم می‌شود (فقط مطب خودش را می‌بیند)
    │
    ├── «ثبت بیمار جدید» را انتخاب می‌کند
    │
    ├── فرم ثبت:
    │   ├── نام کامل (الزامی)
    │   ├── شماره تماس (الزامی)
    │   ├── کد ملی (اختیاری)
    │   ├── تاریخ تولد (اختیاری)
    │   ├── جنسیت
    │   └── گروه خونی (اختیاری)
    │
    ├── ذخیره
    │
    └── سیستم:
        ├── بیمار در لیست بیماران مطب ظاهر می‌شود
        ├── پزشک هنگام شروع ویزیت، بیمار را با اطلاعات آماده می‌بیند
        └── منشی می‌تواند بعداً اطلاعات پایه را ویرایش کند
```

### ۶.۳. جست‌وجوی بیمار قبلی (توسط منشی)

- منشی می‌تواند بیمار قبلی را با نام یا شماره تماس جست‌وجو کند
- فقط بیماران مطب خودش نمایش داده می‌شود
- اطلاعات پایه قابل مشاهده و ویرایش است
- جزئیات پزشکی (ویزیت‌ها، تشخیص‌ها) قابل مشاهده نیست

## ۷. پنل پزشک — تغییرات نسبت به فاز ۱

### ۷.۱. امکانات جدید در پنل پزشک

- انتخاب مطب فعال (اگر چند مطب دارد) از منوی بالا
- مشاهده‌ی بیماران از تمام مطب‌ها (با فیلتر بر اساس مطب)
- بخش «ارتباطات» برای مدیریت اتصال با سایر پزشکان
- بخش «بیماران مشترک» برای مشاهده‌ی بیمارانی که دیگران با او به اشتراک گذاشته‌اند
- بخش «اشتراک من» برای مدیریت طرح پرداخت

### ۷.۲. سوییچ بین مطب‌ها

```
پزشک وارد سیستم می‌شود
    │
    ├── اگر چند مطب دارد:
    │   ├── در هدر: نام مطب فعال + آیکون سوییچ
    │   ├── با کلیک: لیست مطب‌ها نمایش داده می‌شود
    │   └── با انتخاب مطب: داشبورد آن مطب بارگذاری می‌شود
    │
    └── «همه‌ی مطب‌ها» — نمای یکپارچه از تمام بیماران
```

## ۸. نکات پیاده‌سازی

### ۸.۱. Middleware احراز هویت و مجوز

```typescript
// ساختار پیشنهادی middleware (شبه‌کد)
function authMiddleware(req) {
  // ۱. بررسی توکن JWT
  // ۲. استخراج userId و role
  // ۳. افزودن به context درخواست
}

function authorize(...allowedRoles) {
  return function(req) {
    // بررسی نقش کاربر در برابر نقش‌های مجاز
    if (!allowedRoles.includes(req.user.role)) {
      return 403 Forbidden
    }
  }
}

// استفاده:
// GET /api/v1/admin/users → authMiddleware + authorize('admin')
// POST /api/v1/patients   → authMiddleware + authorize('doctor', 'receptionist')
// POST /api/v1/visits     → authMiddleware + authorize('doctor')
```

### ۸.۲. Row-Level Security

```typescript
// هر کوئری بیمار باید شامل فیلتر دسترسی باشد:
// - پزشک: بیماران ایجادشده توسط خودش + بیماران به اشتراک گذاشته‌شده
// - منشی: بیماران مطب خودش
// - ادمین: همه (با لاگ ممیزی)
```

> **قابلیت گسترش:** با افزودن تخصص‌ها و نقش‌های جدید (مثلاً پرستار، تکنسین آزمایشگاه)، می‌توان ردیف‌های جدید به ماتریس دسترسی اضافه کرد. ساختار RBAC طوری طراحی شده که گسترش‌پذیر باشد.
