### ۱.۲. فلسفه‌ی طراحی طرح‌ها

- **آزمایشی:** بدون نیاز به کارت بانکی، ۱۴ روز کامل. هدف: پزشک وابسته شود و خودش تصمیم به خرید بگیرد.

- **نقره‌ای:** برای پزشکان با چند مطب و تعداد بیمار بالاتر — مناسب متخصصین.
- **طلایی:** برای پزشکان پرمراجعه، مراکز درمانی کوچک — شامل AI و بدون محدودیت.

### ۱.۳. محدودیت‌ها و اعمال آن‌ها (Plan Enforcement)

#### سقف بیمار

```
هنگام ایجاد بیمار جدید:
    │
    ├── شمارش بیماران فعال پزشک
    │
    ├── اگر تعداد < سقف طرح:
    │   └── ایجاد بیمار → موفق
    │
    └── اگر تعداد >= سقف طرح:
        ├── نمایش پیام: «شما به سقف بیماران طرح [نام] رسیده‌اید»
        ├── پیشنهاد ارتقای طرح
        └── جلوگیری از ایجاد بیمار جدید
```

#### سایر محدودیت‌ها

- **تعداد مطب:** بررسی هنگام «افزودن مطب»
- **تعداد منشی:** بررسی هنگام درخواست ادمین برای اختصاص منشی
- **تعداد ارتباطات:** بررسی هنگام ارسال درخواست ارتباط
- **قابلیت‌های قفل‌شده:** UI به‌جای حذف کامل، قابلیت را با آیکون قفل و پیام ارتقا نمایش می‌دهد

### ۱.۴. ارتقا و کاهش طرح

#### ارتقا (Upgrade)

```
پزشک وارد صفحه‌ی «اشتراک من» می‌شود
    │
    ├── طرح فعلی نمایش داده می‌شود
    ├── دکمه‌ی «ارتقا» در کنار طرح‌های بالاتر
    │
    ├── انتخاب طرح جدید:
    │   ├── نمایش تفاوت قیمت (pro-rata)
    │   ├── مبلغ باقی‌مانده‌ی دوره‌ی فعلی کسر می‌شود
    │   └── هدایت به درگاه پرداخت
    │
    └── پس از پرداخت موفق:
        ├── طرح بلافاصله فعال می‌شود
        ├── محدودیت‌ها به‌روز می‌شوند
        └── ثبت تراکنش در PaymentTransaction
```

#### کاهش (Downgrade)

```
پزشک طرح پایین‌تر انتخاب می‌کند
    │
    ├── بررسی سازگاری:
    │   ├── اگر تعداد بیماران > سقف طرح جدید:
    │   │   └── هشدار: «شما [تعداد] بیمار دارید اما طرح [نام] فقط [سقف] بیمار را پشتیبانی می‌کند»
    │   │       └── بیماران حذف نمی‌شوند، اما ایجاد بیمار جدید مسدود می‌شود
    │   │
    │   ├── اگر تعداد مطب‌ها > سقف طرح جدید:
    │   │   └── هشدار مشابه
    │   │
    │   └── اگر سازگار:
    │       └── ادامه
    │
    └── کاهش در پایان دوره‌ی فعلی اعمال می‌شود (نه بلافاصله)
```

## ۲. سیستم پرداخت دوره‌ای

### ۲.۱. مکانیزم شارژ دوره‌ای

```
                    ┌─────────────────────────────────────┐
                    │         چرخه‌ی پرداخت                 │
                    │                                     │
    ┌───────┐      │  ┌──────┐    ┌─────────┐    ┌────┐  │
    │ ثبت‌نام │──────►│ Trial │───►│ پرداخت  │───►│فعال│  │
    └───────┘      │  │۱۴ روز│    │  اول    │    │    │  │
                    │  └──────┘    └─────────┘    └──┬─┘  │
                    │                                │    │
                    │              ┌─────────────────┘    │
                    │              ▼                       │
                    │   ┌──────────────────┐              │
                    │   │ پایان دوره        │              │
                    │   │ (ماهانه/سالانه)   │              │
                    │   └────────┬─────────┘              │
                    │            │                         │
                    │   ┌────────┴────────┐               │
                    │   ▼                 ▼               │
                    │ شارژ خودکار     شارژ دستی           │
                    │ (اگر فعال)      (یادآوری)           │
                    │   │                 │               │
                    │   ▼                 ▼               │
                    │ موفق → تمدید    مهلت ۷ روز         │
                    │                     │               │
                    │              ┌──────┴──────┐        │
                    │              ▼             ▼        │
                    │           پرداخت      منقضی        │
                    │           → تمدید     (محدودشده)    │
                    └─────────────────────────────────────┘
```

### ۲.۲. وضعیت‌های اشتراک

| وضعیت | توضیح | دسترسی |
|-------|-------|--------|
| `active` (فعال) | پرداخت انجام شده، دوره معتبر | کامل |
| `past_due` (معوق) | دوره تمام شده، مهلت ۷ روزه | کامل + هشدار |
| `expired` (منقضی) | مهلت تمام شده، پرداخت نشده | فقط‌خواندنی (بدون ایجاد بیمار/ویزیت جدید) |
| `cancelled` (لغو شده) | کاربر لغو کرده | فعال تا پایان دوره، سپس منقضی |

### ۲.۳. سیاست‌های مهم

- **مهلت پرداخت (Grace Period):** ۷ روز پس از پایان دوره — دسترسی کامل با هشدار تمدید.
- **پس از انقضا:** داده‌ها حذف **نمی‌شوند**. پزشک می‌تواند داده‌های قبلی را ببیند اما ویزیت یا بیمار جدید ثبت نکند.
- **شارژ خودکار:** اختیاری — پزشک می‌تواند شارژ خودکار را فعال/غیرفعال کند.
- **فاکتور:** برای هر پرداخت، فاکتور دیجیتال صادر و در پروفایل قابل دانلود باشد.

### ۲.۴. درگاه پرداخت

> **تصمیم باز:** انتخاب درگاه پرداخت ایرانی (زرین‌پال، آیدی‌پی، صداد، بانکی مستقیم) بر اساس هزینه‌ی کارمزد، پایداری API، و پشتیبانی از پرداخت دوره‌ای تصمیم‌گیری خواهد شد.

#### ساختار پیشنهادی یکپارچه‌سازی

```typescript
// لایه‌ی انتزاعی درگاه پرداخت (شبه‌کد)
interface PaymentGateway {
  // ایجاد درخواست پرداخت
  createPayment(amount: number, description: string, callbackUrl: string): Promise<{
    paymentUrl: string;  // URL هدایت کاربر به درگاه
    authority: string;   // شناسه‌ی تراکنش
  }>;

  // تأیید پرداخت (بعد از بازگشت از درگاه)
  verifyPayment(authority: string, amount: number): Promise<{
    success: boolean;
    refId: string;       // شناسه‌ی مرجع بانکی
  }>;
}

// پیاده‌سازی برای هر درگاه جداگانه
class ZarinPalGateway implements PaymentGateway { ... }
class IDPayGateway implements PaymentGateway { ... }
```

> نکته: استفاده از لایه‌ی انتزاعی (`PaymentGateway` interface) باعث می‌شود تغییر درگاه در آینده بدون تغییر منطق کسب‌وکار ممکن باشد.

### ۲.۵. جریان پرداخت

```
پزشک طرح مورد نظر را انتخاب می‌کند
    │
    ├── انتخاب دوره: [ماهانه | سالانه]
    ├── نمایش مبلغ نهایی (با/بدون تخفیف)
    │
    ├── دکمه‌ی «پرداخت»
    │   ├── ایجاد رکورد PaymentTransaction (status: pending)
    │   ├── ایجاد درخواست پرداخت در درگاه
    │   └── هدایت به صفحه‌ی درگاه بانکی
    │
    ├── بازگشت از درگاه:
    │   ├── بررسی (verify) تراکنش
    │   │
    │   ├── اگر موفق:
    │   │   ├── به‌روزرسانی PaymentTransaction (status: success)
    │   │   ├── ایجاد/تمدید DoctorSubscription
    │   │   ├── نمایش پیام موفقیت + فاکتور
    │   │   └── ثبت در لاگ ممیزی
    │   │
    │   └── اگر ناموفق:
    │       ├── به‌روزرسانی PaymentTransaction (status: failed)
    │       ├── نمایش پیام خطا
    │       └── امکان تلاش مجدد
    │
    └── Job دوره‌ای (Cron):
        ├── بررسی اشتراک‌های نزدیک به انقضا (۳ روز قبل → ایمیل یادآوری)
        ├── بررسی اشتراک‌های منقضی‌شده (تغییر وضعیت به past_due)
        └── بررسی past_due بیش از ۷ روز (تغییر وضعیت به expired)
```

## ۳. نقشه‌راه هوش مصنوعی (AI Integration)

### ۳.۱. چشم‌انداز

هدف نهایی: پزشک با **کمترین تعامل دستی** بتواند نتایج معاینه و تشخیص را ثبت کند. AI باید حس **حرفه‌ای و ممتاز (premium)** به تجربه‌ی کاربری بدهد.

### ۳.۲. فازبندی AI

#### فاز AI-1: تبدیل گفتار به متن (STT — Speech-to-Text)

**هدف:** پزشک به‌جای تایپ، صحبت می‌کند و سیستم متن را به فیلدهای ساختاریافته نگاشت می‌کند.

```
پزشک دکمه‌ی میکروفون را فشار می‌دهد
    │
    ├── ضبط صدا شروع می‌شود (با نشانگر بصری)
    │
    ├── پزشک صحبت می‌کند:
    │   مثال: «بیمار با سردرد شدید از دیروز مراجعه کرده.
    │          فشار خون ۱۴ روی ۹. ضربان ۷۸.
    │          معاینه‌ی عصبی طبیعی.
    │          تشخیص: میگرن بدون اورا.»
    │
    ├── پایان ضبط (دکمه‌ی توقف یا سکوت خودکار)
    │
    ├── ارسال صدا به سرویس STT
    │   └── دریافت متن خام
    │
    ├── پردازش NLP:
    │   ├── استخراج شکایت اصلی → «سردرد شدید» → نگاشت به chiefComplaintIds
    │   ├── استخراج علائم حیاتی → فشار: 140/90, ضربان: 78 → پر کردن vitals
    │   ├── استخراج یافته‌های معاینه → «معاینه‌ی عصبی طبیعی» → examFindingsIds
    │   └── استخراج تشخیص → «میگرن بدون اورا» → diagnosisIds
    │
    ├── نمایش نتیجه به پزشک:
    │   ├── فیلدهای فرم به‌صورت خودکار پر شده‌اند
    │   ├── هر فیلد با هایلایت زرد مشخص شده (= پیشنهاد AI)
    │   ├── پزشک می‌تواند هر فیلد را تأیید، ویرایش یا حذف کند
    │   └── ⚠️ هیچ فیلدی بدون تأیید پزشک ذخیره نمی‌شود
    │
    └── تأیید نهایی → ذخیره‌ی ویزیت
```

**اصل ایمنی حیاتی:** هر خروجی AI صرفاً «پیشنهاد» است. پزشک باید قبل از ذخیره، آن را بررسی و تأیید کند. سیستم هرگز خودکار ذخیره نمی‌کند.

#### فاز AI-2: پیشنهاد هوشمند تشخیص

**هدف:** بر اساس شکایت اصلی و علائم حیاتی، تشخیص‌های محتمل پیشنهاد شوند.

```
پزشک شکایت اصلی و یافته‌های معاینه را ثبت می‌کند
    │
    ├── سیستم بر اساس الگوهای ثبت‌شده:
    │   ├── تشخیص‌های مرتبط را رتبه‌بندی می‌کند
    │   └── ۳ تا ۵ تشخیص محتمل پیشنهاد می‌دهد
    │
    ├── نمایش به‌صورت dropdown/chip:
    │   ├── «تشخیص‌های پیشنهادی:»
    │   ├── [میگرن بدون اورا — ۸۵٪]
    │   ├── [سردرد تنشی — ۶۵٪]
    │   └── [فشار خون بالا — ۴۰٪]
    │
    └── پزشک انتخاب می‌کند یا تشخیص دیگری وارد می‌کند
```

#### فاز AI-3: تکمیل هوشمند فرم

**هدف:** بر اساس تاریخچه‌ی بیمار و الگوهای قبلی پزشک، فرم ویزیت از پیش پر شود.

```
پزشک ویزیت جدید برای بیماری که قبلاً مراجعه کرده شروع می‌کند
    │
    ├── سیستم بر اساس ویزیت‌های قبلی:
    │   ├── بیماری‌های مزمن بیمار → خودکار در فرم
    │   ├── داروهای فعلی → نمایش به‌عنوان یادآوری
    │   └── آخرین علائم حیاتی → مقایسه با مقادیر جدید
    │
    └── نکته: فقط پیشنهاد — پزشک باید تأیید کند
```

### ۳.۳. استراتژی بهینه‌سازی هزینه‌های زیرساخت AI

با توجه به هزینه‌های بسیار بالای اجاره سرورهای GPU در ایران (ماهانه ۱۰۰ تا ۳۰۰ دلار فقط برای سخت‌افزار پایه)، راه‌اندازی مدل سلف‌هاست (Self-hosted Whisper) از نظر اقتصادی در مراحل اولیه توجیه ندارد. در عوض، رویکرد **API-First (Cost-Optimized)** پیشنهاد می‌شود:

| لایه پردازش | گزینه پیشنهادی | مزیت اقتصادی و فنی |
|-------------|----------------|--------------------|
| **STT (تبدیل صوت به متن)** | **Groq API (Whisper-Large-V3)** | سرعت پردازش فوق‌العاده بالا (Real-time). هزینه به شدت پایین‌تر از اجرای محلی GPU. |
| **NLP (استخراج و نگاشت ساختاریافته)** | **DeepSeek-V3 / Qwen-Max API** | عملکردی هم‌تراز با GPT-4o در زبان فارسی و درک پزشکی، اما با هزینه‌ای معادل کسری از سنت (کمتر از 0.14$ به ازای یک میلیون توکن). |
| **ارائه‌دهندگان داخلی** | APIهای ایرانی مبتنی بر مدل‌های اپن‌سورس | هزینه‌ی ریالی و عدم وابستگی به پرداخت ارزی (در صورت وجود مدل با دقت کافی در اصطلاحات پزشکی). |

> **توصیه اجرایی:** استفاده از Groq برای تبدیل صوت و DeepSeek برای NLP. این ترکیب کیفیت بسیار بالایی در زبان فارسی دارد و هزینه پردازش هر ویزیت را به شدت کاهش می‌دهد که در مقایسه با خرید و نگهداری سرور GPU، صرفه‌جویی عظیمی در هزینه‌های نگهداری (Maintenance) ایجاد می‌کند.

### ۳.۴. ملاحظات حریم خصوصی در استفاده از APIهای خارجی

از آنجا که از APIهای ابری (به‌جای مدل‌های محلی) استفاده می‌شود، رعایت اصول زیر الزامی است:
- **بی‌نام‌سازی (De-identification):** پیش از ارسال هر متنی به سرویس NLP ابری (DeepSeek و ...)، هیچ‌گونه اطلاعات هویتی (مثل نام بیمار، کد ملی، شماره تلفن) **نباید** در Prompt قرار گیرد. فقط متن خام پزشکی ارسال می‌شود.
- **سیاست نگهداری داده‌ها (Zero Data Retention):** استفاده از API providerهایی که سیاست "عدم استفاده از داده‌های API برای آموزش مدل" (No Training on API Data) را تضمین می‌کنند.
- **عدم ذخیره صوت:** فایل صوتی بلافاصله پس از تبدیل به متن از حافظه موقت سرور حذف شده و فقط متن آن در دیتابیس (پس از تأیید پزشک) ذخیره می‌گردد.
- **لاگ استفاده:** ثبت توکن‌های مصرفی و APIهای فراخوانی شده برای محاسبه دقیق هزینه به ازای هر پزشک/طرح اشتراک.

### ۳.۵. تجربه‌ی کاربری AI — اصول طراحی

- **حس Premium:** انیمیشن‌های روان هنگام ضبط صدا (مثلاً موج صوتی متحرک)، بازخورد بصری هنگام پردازش.
- **سرعت:** پردازش صوت باید در کمتر از ۵ ثانیه نتیجه دهد — در غیر این صورت پزشک به تایپ دستی برمی‌گردد.
- **Fallback روان:** اگر AI نتواند بخشی را تشخیص دهد، آن بخش خالی بماند و پزشک دستی پر کند — نه خطا.
- **آموزش تدریجی:** با بازخورد پزشکان (تأیید/ویرایش پیشنهادات)، مدل به‌مرور دقیق‌تر شود.
